# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

- **Server/ops engineers**: run the script on a Windows Server (usually through OpenText Server Automation) before an upgrade window, then read the per-server report to fix findings.
- **Upgrade leads / change managers**: read the fleet overview to decide which servers are ready, worst first, and to plan windows.
- **Auditors / customer reviewers**: receive a shared report as evidence of readiness.

## Product Purpose

Read-only in-place upgrade (IPU) readiness assessment for Windows Server (targets 2025 default, 2022, 2019). Gives one overall status, a prioritised list of what to fix, and a self-contained report; a second run after the upgrade compares the server against its own pre-upgrade baseline. `Merge-IPUAssessments.ps1` rolls many results into a fleet overview. Success: an operator knows exactly what blocks the upgrade and what to do, and a lead can see the whole estate at a glance.

## Positioning

Non-remediating, one-file assessment that runs inside the operator's existing automation platform and answers four questions (supported path, workloads survive, Windows healthy, nothing lost afterwards), with a before/after baseline comparison of the same server.

## Operating Context

- Script runs on target servers under Windows PowerShell 4.0+; shipped as one `.ps1` built from parts in `src/`.
- Outputs per server: HTML report, result JSON, log, one semicolon-delimited result line. Fleet: overview HTML plus CSV sheets.
- Reports may be collected, shared and printed; evidence copies are kept apart because they are not redacted.

## Capabilities and Constraints

- Statuses include overall status, `PARTIAL` (checkpoint), `SPECIAL` (cluster nodes, domain controllers), and `MANUAL` when a check errors; failures must never look clean.
- Windows Server editions only; no workstation Windows, no Linux.
- HTML is generated by PowerShell code in `src/assessment/` and `src/merge/`: ASCII-only source, CRLF, PS 4.0 compatible. Edit parts, rebuild, never edit built files.
- Terminology lives in `GLOSSARY.md`.

## Brand Commitments

None established; no logo or visual identity recorded. Visual world undecided.

## Evidence on Hand

Sample reports and examples under `docs/samples/` and `docs/examples/`; result schema in `docs/result-schema.md`. No host data, real hostnames or customer names may appear in the repo.

## Product Principles

1. Failures stay visible: an error is shown as manual follow-up, never as a clean result.
2. Findings are prioritised and actionable: what to fix first, and how.
3. A report is a self-contained artifact: single file, opens offline, safe to share.
4. The fleet view is worst-first: the reader sees what needs attention before anything else.
5. Read-only and honest: the tool never changes the server and never overstates certainty.

## Accessibility & Inclusion

- Single self-contained HTML file: no external CSS, JS, fonts or images.
- Print (PDF) and dark mode must both work.
- WCAG AA: status never conveyed by color alone; keyboard and screen-reader usable.

## Surfaces in scope for design work

Per-server HTML report, fleet overview HTML, and docs / user guide (README and `docs/`).
